Consequences of WSL2 that constrain the program:

- No CPU governor and no `intel_pstate/no_turbo` in the guest (`not exposed
  (WSL)`). Frequency scaling is owned by the Windows host and **cannot be
  frozen from inside**. This is the single largest uncontrolled variable; it is
  why every result must be reported as an A/B **ratio measured in the same
  session**, never as an absolute number compared across days.
- `ethtool` is unavailable, so NIC coalescing, ring sizes and per-queue drops
  are not observable. Only `ip -s link` counters are.
- Hugepages: `HugePages_Total: 0`, THP mode `[madvise]` → no THP for the
  allocator unless explicitly madvised.
- `hv_utils.timesync_implicit=1` and **zero** loaded `hv_utils` modules: guest
  clock is slaved to the Windows host, and there is no in-guest NTP client
  binary (`chronyc`, `ntpq`, `ntpdate` all absent). See §7.

Note: 8 physical cores visible, not the 24 of the bare 14900KF — WSL exposes a
16-vCPU slice. `-march=native` = `alderlake` (P-core ISA); if the Windows host
ever schedules the guest on E-cores this is still correct ISA-wise but the
throughput per vCPU is not uniform.

**Pinning map.** No pinning is applied today: arm processes inherit the
full `0-15` affinity mask and are free to migrate. Phase 1 must pin, and the
map below is the one to implement (written here so both arms inherit it
unchanged from a single source):

| cpus | use |
|---|---|
| 0-1 | OS, WSL interop, agent/Hermes, disk I/O threads |
| 2-3 | relay / moqx (when in path) |
| 4-7 | publisher (bench client) |
| 8-11 | subscriber (bench server) |
| 12-15 | spare / repeat runs |

Rationale: keep the two endpoints off the same physical core pairs (0-7 are
SMT siblings of 0-7 in WSL's 8c/2t layout, so 4-7 and 8-11 land on distinct
physical cores), and never co-schedule a noisy agent with an endpoint.

`/sys` reports 10 Gb/s. In WSL2 this is a synthetic link rate: the real path
is vNIC → Windows vSwitch → physical NIC. **The 10 Gb/s figure is therefore
not evidence of 10 Gb/s achievable goodput**; treat it as "not the bottleneck
we think it is" and calibrate with a measured number before Phase 1 makes any
bandwidth claim. Calibration candidate (to run in Phase 1, recorded here so it
is not forgotten): `iperf3 -u -b 0 -t 10` over `lo`, plus the loopback bench
throughput already observed (§8, 1068.5 Mbps at 4096 B objects).

Two of these will bind before any protocol-level difference does, so they are
part of the frozen baseline rather than a "tuning" step:

- `rmem_max = wmem_max = 208 KiB`: a QUIC socket that asks for a larger buffer
  is silently clamped. Both arms get the same ceiling, so the A/B stays valid,
  but a 1 Gb/s+ stream with a 24 ms RTT needs ≈3 MB in flight — the socket
  buffer is the first ceiling we will hit.
- `ulimit -n` soft = 4096: at `-P 8` and one socket per stream-crossing this is
  ample, but a sweep to `-P 512` is not. Raise per-run (`ulimit -n 65536`),
  never globally, and record it per run.

Frozen decision: **do not change any sysctl or qdisc for Phase 0 or Phase 1.**
If a tweak is later shown to matter, it goes in `perf/release-sweep/tweaks/`
as its own card with both arms re-measured, and `env-freeze.md` gets a new
section — never an edit.

## 7. Clock offset procedure

Facts: `timedatectl` → `Time zone: America/New_York (EDT, -0400)`,
`System clock synchronized: yes`, `NTP service: active` (systemd-timesyncd);
no `chronyc`/`ntpq`/`ntpdate`; `hv_utils` modules loaded: 0;
kernel cmdline has `hv_utils.timesync_implicit=1`.

Procedure to use whenever a latency number is taken:

1. Before each run, `date -Is` and `python -c "import time; print(time.clock_gettime_ns(time.CLOCK_REALTIME), time.clock_gettime_ns(time.CLOCK_MONOTONIC))"` → record the offset pair in the run manifest.
2. If the run reports one-way delays (it does: `loopback_bench` reports
   latency from `loc` timestamps), the offset error between endpoints is the
   measurement error. For **loopback** (single clock) offset is zero by
   construction — which is the main reason Phase 1's first pass stays on
   loopback.
3. For any two-machine run, do not trust one-way delay until the measured
   offset is an order of magnitude below the delay being claimed; otherwise
   report RTT only. Never compare a one-way delay from host A against one from
   host B.
4. Re-check after suspend/resume: WSL2 clock jumps are a known failure mode,
   and the guest has no NTP client of its own to correct them.

Two consequences found during the smoke, both recorded because they change
what a probe result *means*:

1. The relay's TLS is `insecure: true`, so a probe **must** pass `-k`, else
   the handshake fails on certificate verification and the failure has nothing
   to do with MoQ. `logs/smoke/relay_probe.no-insecure.attempt1.log` is that
   first, unrepresentative attempt; it is kept so the mistake is not repeated
   silently.
2. The running binary (`build/moqx`, mtime 2026-10-25) is **newer than the
   process** (started 2026-10-22; `/proc/1492225/exe` → `(deleted)`). The
   process is therefore an older build than the tree on disk, and its ALPN set
   is whatever that build offered. Measured with a forced-ALPN probe
   (`/home/gmarzot/.hermes/cache/scratch/probe_alpn.py`, throwaway): the relay
   accepts `moqt-16` and rejects `moq-00`, `moqt-14`, `moqt-18`,
   `moqt-16-meta-05` and `h3`. That matches a pre-standard-ALPN MoQ stack. It
   does not block us — the probe negotiates `draft-14,draft-16` in one session
   — but it does mean **the relay is not a draft-18 peer** and must not be
   used to characterise draft-18 behaviour until it is restarted from the
   current build.

## 9. Loose ends

- `python3` on PATH is Hermes' 3.14.9 venv. Every arm command in this document
  names the venv binary explicitly (`arms/<NAME>/venv/bin/python`) and passes
  `-P`, because a directory named `aiomoqt` in an ancestor CWD shadows the
  installed package.
- `-march=native` bakes this host into the wheel. Wheels are therefore **not
  portable**; a wheel built on another machine never enters `arms/`.
- `/sys/class/net/eth1/speed` = 10000 is a WSL2 synthetic value (§5).
